## 1. 取りこぼし（`8ddf256`）

### 何が起きていたか

9/1発売の実在の記事が、静かに捨てられていた。

```
秋限定「縁結びのご塩アイス 万福のお芋」（株式会社静岡木工）
→ 1回目: アイス関連語なし
→ 2回目: 発売告知を示す語なし
```

### なぜ落ちたか

2つの独立した原因が重なっていた。

1. タイトルに「アイス」があっても、本文に文脈語（冷凍・カップ等）が揃わないと落としていた
2. 告知語の一覧に「販売」「限定」が無く、**「秋季限定〜販売いたします」型の告知**を告知と認識できなかった

大手ほどリリースが長く文脈語が揃う。**この規則だと、中小・地方メーカーばかりが漏れる。**

### 直した内容

- タイトルに「アイス／冷菓／フローズン」があれば、それだけで候補に通す
- 告知語を語幹化（「販売」「限定」「先行」）
- **除外理由をログに残す**。これが無かったから気づくのが遅れた

### 教訓

**「なぜ落としたか」が出ていない仕組みは、落としたことに気づけない。**
投稿件数のログはあったが、除外理由が無かった。次に何かを落とす判断を足すときは、
必ず理由をログに出すこと。

## 3. 自動投稿を大手に限る（`e6a56a3` → `227d3b7`）

### 決めたこと

> 大手流通メーカーのアイスは自動投稿してもいいけど、今回の静岡木工の情報などは、一度確認したい

事実照合を通っても、中小・地方メーカーのリリースは書式が不揃いで、
「照合は通るが読むと違和感が残る」投稿が起きうる。

配信元の一覧を作り、そこに載っている配信元だけを自動投稿の対象にした。
判定は配信企業名（`dc:corp` / `dc:creator`）のみ。**Claude が抽出した `maker` は使わない。**
抽出結果で自動投稿の門を開けると、抽出を誤ったときにそのまま外へ出る。

### そして、その日のうちに直した（`227d3b7`）

最初は**部分一致**で照合していた。本人側のレビューで指摘を受けた。

```
「ロッテ」  → 【ロッテリア】が通る
「イオン」  → 【イオンディライト】【イオンファンタジー】が通る
「明治」    → 【明治安田生命】【明治座】が通る
```

このとき私は「アイス語・Claudeの判定・事実照合の3関門があるので実質起きない」と
評価した。**これは誤りだった。**

ロッテリアはソフトクリームや冷菓の新商品リリースを**現実に出しうる**。
つまり3関門をすべて**正当に通過して**外へ出る。

> 3関門は「誤情報」を止めるものであって、「配信元の取り違え」を止めるものではない。

守るべき対象を取り違えた評価だった。正規化後の完全一致に変更し、
グループ会社は1社ずつ列挙する方式にした。書き漏らした会社は承認待ちに回るだけなので、
**外れ方が安全な側に倒れる。**

`trust.ts` と `CLAUDE.md` の両方に「部分一致に戻さないこと」と理由を残した。

## 5. @Press を情報ソースに追加（`bb1f51b`）

> クラシエ株式会社、株式会社ブルボン、など、他のメーカーでもアイスの情報として有力であれば拾いたい

PR TIMES を使わず @Press で配信するメーカーがある。取りこぼしの構造的な原因だった。

- `https://www.atpress.ne.jp/rss/index.rdf`（robots.txt で `/rss/` は許可を確認）
- RSS 2.0。配信企業名が `dc:creator`、日時が `pubDate`
- **既存のパーサが両方読めたので、パーサ側の変更はゼロ**
- 記事ページの `<title>` が「タイトル | 会社名」なので、配信元の取り方だけ分岐

実測: PR TIMES 200件 + @Press 100件 = 取得300件。
しかも**@Press のほうが鮮度が高い**（2分前 vs 21分前）。

### バリュープレスを入れなかった理由

**robots.txt が `/rss/` `/alliance_media_rss/` `/api/` を全ユーザーエージェントに
対して Disallow している。** 一覧ページもサーバー側でHTMLを返さない。

技術的に回避する手はあるが、相手が明示的に拒否している経路を叩くことになる。
入れるなら許諾を取るのが先。**ここは勝手に外さないこと。**

## 6. 記事の種類（`b8df7d5`）

@Press を入れた最初のスキャンで、こういう記事が拾えた。

```
ソフトクリーム専門店「MINI SOF」イクスピアリ1F に期間限定で出店
（@Press 経由。PR TIMES には無かった）
```

判定は「対象外」。イベント・店舗オープンであって発売告知ではない。
機械としては正しい。**しかし本人の答えはこうだった。**

> 期間限定出店（イベント・店舗オープン）の告知でもミニソフは話題性があるので取り上げたい

「発売告知かどうか」の1本だけで切っていたのが設計の誤りだった。
Claude に `topic_type` を選ばせ、種類ごとに扱いを分ける。

| topic_type | 扱い |
| --- | --- |
| `new_product` | 通常経路（自動投稿の可能性あり） |
| `store` / `event` / `collab` | **必ず承認待ち。投稿文は作らない** |
| `other_ice` / `not_ice` | 捨てる |

あわせて事前フィルタから「イベント開催」「出展」「キャンペーン開催」を外した。
**種類の判断は Claude に任せ、事前フィルタは広く通す**方針に変えた。

## 8. スマホ通知（`4b6bcb4`）

> 常に、admin画面を覗きたくない。通知が来たらアドミンを覗きにいく感じにしたい

Android + PWA なので Web Push を採用（追加アプリ不要）。

設計で気をつけた点:

- **1回のスキャンにつき通知は1通。** `tag` を固定して積み上がりを防ぐ。
  まとめて記事が出た日に10分おきの連打にならないように
- **404 / 410 が返った購読はその場で削除。** 放置すると毎回失敗して
  「いつの間にか届かなくなった」になる
- **通知の失敗はスキャンを止めない。** 投稿の可否とは無関係
- VAPID鍵が未設定でも動く（送信をスキップしてログに残すだけ）

鍵の生成スクリプトは Node 標準の crypto だけで書いた。
`web-push` を入れる前に動く必要があるため。**秘密鍵は本人の端末でのみ表示する。**

実機で着信を確認済み。

## 9. 人の判断を記録する（`74400f9`）

> 承認しなかった情報などの理由を書いて、その理由を活かしてシステムの管理精度を
> 向上させていくような仕組みはできるかな？

これまで却下は guid を捨てるだけで、**なぜ却下したのかがどこにも残っていなかった。**
一番価値のあるデータを毎回捨てていた。

2種類を記録する。

- `reject` … 定型の理由コード（8種）＋任意メモ＋Claudeが書いた文面
- `edit` … 承認前に文面を書き換えたときの「元の文 → 実際に出した文」

**`edit` のほうが価値が高い。** 却下は「ダメだった」しか分からないが、
編集差分には「どう直せば正解か」が入っている。しかも本人は普段どおり
直して投稿するだけでよく、追加の手間がゼロ。

記録の失敗は却下・投稿の操作を止めない。**記録は目的ではなく材料であって、
本来の操作を巻き添えにしてはいけない。**

### 集計画面を作らなかった理由

母数が足りないうちに集計を見せると、偶然を傾向と読み違える。
判断材料にならない画面は、あると逆に間違った判断を誘発する。

## 10. 文体の見本の自動更新（`aacc4b7`）

プロンプトの文体見本が固定だったため、**承認時に文面を直しても次の生成に
反映されず、毎回同じ直しが発生していた。**

`/admin` で承認して投稿した文を、次回以降の見本にする。

歯止め4つ:

1. **自動投稿された文は見本にしない。** 人が読んで通した文だけを材料にする。
   Claude の出力をそのまま学習材料にすると、癖がそのまま固定される
2. **発売告知だけ。** 出店・イベントの告知は形式が違うので混ぜると崩れる
3. **新しい順に3本だけ。** LPUSH + LTRIM で書き込み時に上限を固定するので、
   読むのは LRANGE 1回。スキャンごとのコマンドが増えない
4. **失敗しても止まらない・戻せる。** 取得に失敗したら固定見本で続行。
   `v2:style` を空にすればいつでも元に戻る

出力を入力に還流させる仕組みなので、自己増幅への歯止めを設計の中心に置いた。
