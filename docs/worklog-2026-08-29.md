## 1. 発端と、本当の原因

### 症状
「以前作った bot がバグだらけで機能していない」。投稿が1件も出ない状態が続き、
コードを何度も書き直しても改善しなかった。

### 真の原因（Vercel の本番ログから特定）

**Upstash Redis のデータベースが消滅していた。**

```
Cronジョブエラー: [TypeError: fetch failed]
  cause: Error: getaddrinfo ENOTFOUND direct-lemur-82033.upstash.io
```

cron は24時間で8回動き、**8回とも同じエラーで500終了**していた。
毎回「PR TIMES から444件取得 → Redis に問い合わせ → 名前解決失敗 → 500」を
繰り返していただけで、投稿ロジックには一度も到達していなかった。

`.env` の `KV_REST_API_URL` が指すホストが DNS で解決できない状態。
Upstash 側で削除されたか、無料枠の非アクティブ回収で消えたと見られる。

### ここから得た教訓

**コードのバグではなく「直す対象を間違えていた」ことが、時間を溶かした最大の原因。**
承認制ワークフローに作り替えても下書きが1件も出なかったのも、同じ理由だった。

この経験から `/api/selftest` を作った。依存先（RSS・Redis・Claude・X認証・
画像アップロード）を一括で叩き、**どこが死んでいるかを名指しで報告する**。
次に「動かない」と感じたら、コードを読む前にここを叩く。

## 2. 旧実装（v1）に実在した問題

原因は Redis だったが、コード側にも構造的な問題が複数あった。

| 問題 | 影響 |
|---|---|
| 画像アップロードが廃止済みの `upload.twitter.com/1.1/media/upload.json` | 画像が付かない／投稿失敗 |
| `redis.keys()` を記事ごとに実行し、1件ずつ GET | Upstash は1コマンド1HTTP。数千往復してタイムアウト |
| 収集先がメーカー15社のRSS固定 | 新興・地方ブランドを永久に取りこぼす |
| キーワードが `"アイス"` のみ | アイスコーヒー等を大量に誤検出（実測444件/回） |
| Claude を2回呼び、片方失敗で状態が不整合 | 発売日は取れたが投稿文が無い、等 |
| 15分ギャップが同一実行内で効く | 実質1実行1投稿。上限3件の設定が無意味 |
| 発売日が近い順に投稿 | 出たての速報が後回しになる |
| cron 設定が vercel.json と外部cronで二重管理 | どちらが動いているか不明 |
| 1日20件（X Free枠の17件/24hを超過） | 上限違反 |
| ローカルとGitHub/Vercelの中身がズレていた | 「直したはずの挙動」と実際の挙動が食い違う |

## 3. v2 の設計

```
PR TIMES 全社RSS(index.rdf / 約150件 = 直近2時間)   ← 10分おき
  ↓ 事前フィルタ（正規表現のみ・API費用ゼロ。99%以上をここで落とす）
  ↓ 記事本文を取得（RSS要約は途中で切れるため照合には本文が要る）
  ↓ Claude 1回で「アイスの発売告知か」判定＋項目抽出＋投稿文生成
  ↓ 機械照合  ← 品質の生命線
       全項目クリア   → 自動投稿
       1つでも不一致 → /admin の承認待ち
  ↓ X へ投稿（/2/media/upload → /2/tweets）
```

### 設計上の判断と、その理由

**照合は「原文のどこかにあるか」ではなく「商品名の直後にあるか」で見る**
アイスのプレスリリースは1本で2〜5商品を告知するのが普通。素朴な部分一致だと
商品Aの名前に商品Bの価格を組み合わせても全部通ってしまう。

**Claude 呼び出しは1記事1回**
v1 は「発売日抽出」と「投稿文生成」で2回叩いており、片方だけ成功して
状態が食い違う不整合の原因になっていた。出力形式は `tool_choice` で固定し、
JSONパース失敗というバグ種別ごと無くした。

**`redis.keys()` を全廃**
月次シャードの SET と `SMISMEMBER` で、150件の重複判定を **1コマンド**で行う。
1日144回×150件を1件ずつ問い合わせると月数十万コマンドに達する。

**Vercel cron に一本化**
Pro プランなので10分おきが可能。`CRON_SECRET` は Vercel が Authorization
ヘッダに自動付与するため外部cronは不要。
なお **Vercel の cron は Deployment Protection(SSO) を貫通する**ことを実測で確認。
外部cronだと SSO で弾かれるため、これは重要な違い。

**実行ロック＋記事単位の投稿権**
Vercel の cron は「同じ実行が二重に届くことがある」と公式に明記されている。
ロックが無いと同じ記事を2回投稿しうる。

## 5. 実記事の検証で見つけて直した不具合

合成データでは通っていたものが、実物では次々に落ちた。
**4本中0本しか自動投稿に到達しない**状態から始めて、以下を順に潰した。

### 判定側の誤り

| # | 症状 | 原因 | 対処 |
|---|---|---|---|
| 1 | 商品名が入っているのに「含まれていません」 | `normalize()` が『』「」を除去していなかった。日本語のリリースは商品名を『』で囲むのが通例で、投稿文では外れる | かぎ括弧・引用符・中黒・全角記号（＆％＋－！？：）をまとめて吸収 |
| 2 | 文字数超過で投稿不可（304字・289字） | プロンプトに「280以内」と書くだけで、超えたときのやり直しが無い | 目標を230に下げ、上限を下回るまで最大3回短縮。回ごとに目標を厳しくする |
| 3 | `280円（税込308円）` の税込額が「別商品の価格」 | 商品名の直後の**最初の**価格だけを見ていた | 近接した価格（12字以内）を1つの表記としてまとめる。税表記の探索も直前12字まで拡張 |
| 4 | 発売日が商品名より前にある記事で誤検出 | 「キャンペーン期間：9/1〜」のような配置で、後ろの無関係な日付を採用 | 抽出した発売日の原文表記が実在し、**かつその近く(±300字)でその商品が語られている**場合は抽出を優先 |
| 5 | 商品名の表記ゆれで不一致 | 同じAIが「ANY1 ICE あずき」と「ANY1 ICE CREAMから第三弾『あずき』」を混在させる | 完全一致から「構成語がすべて含まれるか」に変更 |
| 6 | 商品名に「（10フレーバー）」等の補足 | 抽出時に内容量を括弧で付け足す | プロンプトで禁止＋照合時に末尾括弧を除去 |
| 7 | `→` が絵文字判定で投稿不可 | 絵文字の正規表現に矢印(U+2190〜21FF)を含めていた | 矢印を除外。実文体で「濃厚生キャラメル → 8/31(月)発売」と多用される |
| 8 | 有名商品を取りこぼす | RSS要約が切れて「アイス」の語が一度も出ない告知が実在（例：ガリガリ君の新フレーバー） | ブランド名・アイスメーカー名を強いシグナルとして追加 |
| 9 | コラボ商品の二重投稿 | 記事ID単位の重複防止しか無く、両社がリリースを出すと同じ商品が2回流れる | 投稿済み商品名を45日保持。自動・承認の両経路でチェック |

### 検証の作り方で直したこと

**自己診断のテスト画像を外部URL依存から自前生成に変えた**
`selftest` が検証用画像に PR TIMES のロゴURLを決め打ちしており、その画像が
消えて404になった。結果、**肝心の「Xへの画像アップロードが通るか」が
一切検証できていない状態**になっていた。自己診断が第三者の都合で壊れるのは
本末転倒なので、zlib と自前CRC32で PNG をその場で生成する方式に変えた。

**`/api/try` を作った**
アイスの新商品は1日数件しか配信されないため、cronを眺めていても何時間も
何も起きず「実際に来たときちゃんと動くのか」を確かめられない。
記事URLを1本指定して判定〜投稿文生成〜照合まで走らせる窓口を用意した。
投稿も状態の書き換えもしない。フィルタや文体の調整にも使える。

**スキャン結果の要約をログに1行出すようにした**
cronが200で成功しても件数が一切ログに出ず、管理画面を開くまで何が起きたか
分からなかった。`[scan:live] 取得200 新規5 候補0 判定0 投稿0 キュー0 除外5 0.4秒`

## 6. 独立レビューで見つけた欠陥（実機投入前）

書き上げたコードを別途レビューにかけ、13件の欠陥を発見・修正した。重要なもの：

- **承認ボタンと cron が同じ記事を同時に投稿しうる競合** → 記事単位の投稿権で排他
- **投稿がタイムアウトしたとき「失敗」と判断して再投稿する経路** → 投稿されたか
  不明な失敗（タイムアウト・5xx）では再試行しない。4xxのみ「確実に未投稿」と扱う
- **`/2/tweets` に使えない `media_key` を media_id として使う誤り**
- **`fetch` のタイムアウトが本文読み出しをカバーしていない** → 応答が止まった相手に
  実行時間を食い潰される（`clearTimeout` がヘッダ到着時点で走っていた）
- **月末に重複判定が壊れる日付計算** → 5/31 に `setUTCMonth(-1)` すると 4/31 →
  5/1 に正規化され、先月キーが今月キーと同じになる
- **候補が上限を超えた日に古い記事が永久に後回しになる** → 古い順処理に変更

## 7. 環境面で直したこと

**git がファイルを削除できず、コミットやブランチ切替が壊れていた**
`_to_delete/git-lock-cleanup/` や `.git/HEAD.lock` の残骸がその痕跡。
ローカルと GitHub/Vercel の中身がズレて「直したはずなのに直らない」状態に
なっていた物理的な原因はこれ。

**APIキーの流出を GitHub の push protection が阻止**
退避コミットを作る際に `git add -A` を使い、`vercel env pull` が生成した
`.env.check`（Anthropic APIキー入り）を巻き込んでいた。リポジトリが public
だったため危なかった。`.env.*` を一括で `.gitignore` に追加して再発を防止。
**push は拒否されたのでキーは外部に出ていない。ローテーションは不要。**

**改行コードが LF/CRLF で混在**
Windows の `core.autocrlf=true` と `.gitattributes` 不在で、1行直すだけで
全4,245行が差分になっていた。`* text=auto eol=lf` を明示して統一。

## 8. 投稿文の文体

本人の過去の実投稿5本を参照して調整した。

- 冒頭は `【発売情報】`（復活・再販・定番昇格も扱うため「新商品」では実態に合わない）
- 日付は `9/21(月)` のスラッシュ表記。曜日は原文に記載がある場合のみ
- 価格は `価格：216円（税込）`、販売エリアは `販売エリア＝全国` のラベル形式
- 冒頭にフックの一文、締めは「〇〇好きは要チェック」型のファン層への呼びかけ
- `!!` `→` `・` は使用可

**X Premium でも API 経由では280文字（重み）の制限が残る。**
25,000文字の長文投稿はアプリ・Web版の機能で、`POST /2/tweets` からは
Premium アカウントでも投稿できないという報告が開発者フォーラムにある。
そのため `MAX_TWEET_WEIGHT` は 280 のまま（環境変数で変更可）。

## 9. 残っていること

`MAX_DAILY_POSTS=0` のため、**cron が拾って自動でXに投稿されるまでの通しは
まだ一度も走っていない。** 部品はすべて実機で確認済み。

1. `/admin` の「投稿待ち」で溜まった記事の文章を確認
2. Vercel の環境変数 `MAX_DAILY_POSTS` を `0` → `12` にして **Redeploy**
   （環境変数はデプロイ時に取り込まれるため、変更だけでは反映されない）
3. 最初の数件を「投稿済み」タブか Vercel ログで確認

切り替え後に見るべきもの：投稿頻度が実運用で妥当か（1週間）、
承認待ちに回る割合（実記事4本でしか見ていない）。

## 10. 触ってはいけないところ

- `verify.ts` の照合を緩めて「全部自動投稿」にすること。
  これをやると v2 はただの自動投稿Botに戻り、誤情報がそのまま公開アカウントに出る
- `store.ts` に `redis.keys()` を足すこと。v1 のタイムアウト要因
- 実行ロックの削除。Vercel の cron は同じ実行を二重配信しうる
- `.env.check` などをコミットすること。`vercel env pull` の出力は秘密情報を含む
